Why PM behaves this way today

The Pending-approval query has a deliberate escape hatch: a job with no operator behind it stays open to every operator, so it can never end up with nobody able to accept it. Every PM job is generated under the planner/admin account, so it always takes that branch. And the server-side guard starts with if u["role"] != "operator": 403 — so a planner cannot accept anything at all right now, in any screen.

3 · Three things to confirm before I code it

1. Which planner accepts a PM? Any planner in that factory, or only the one who released the job?
→ Recommend: any planner or admin in that factory. One planner on leave must not freeze a week of PM sheets — that is the same reasoning behind the fallback that exists today.
2. IMP (improvement) jobs — planner or reporter? They are raised by the planner, so under a strict "whoever raised it accepts it" rule they go to the planner queue.
→ Recommend: planner queue, same as PM. Say the word if IMP should stay with the operator.
3. A CM/BD whose reporter has left the company (inactive account)? Today an operator-raised job is locked to that person; if the account is gone, nobody can accept it.
→ Recommend: keep the lock, but let any operator in the factory accept when the reporter's account is inactive. Small guard, prevents a stuck job.

4 · What I would change

  • server/jobs.py — signoff endpoint: replace the operator-only gate with a by-jobtype rule. PM/IMP → planner or admin; CM/BD → the reporter (with the inactive-account fallback). The 403 message keeps its bilingual shape.
  • server/jobs.py — view=toapprove: exclude PM/IMP from the operator list, and drop the "no operator behind it" fallback that pulls PM in. Add view=pmapprove for the planner: status='ServiceCompleted' AND jobtype IN ('PM','IMP').
  • server/jobs.py — badge counts and push: the completion push on the ServiceCompleted PATCH currently notifies operators; PM should notify planners instead.
  • server/jobs.py line ~967 — the sign_appr media guard says planner/admin only, while the operator signoff writes that column directly. Once approval is split the two must agree, or a reporter's acceptance signature will hit a 403 the day someone routes it through that endpoint.
  • static/index.html — planner nav gets a รอตรวจรับ tab with badge + lamp; the planner job screen gets the ตีกลับ / ตรวจรับ+เซ็น pair (reuse opApprove / opReject, renamed); the technician's submitted-status line and the operator tab text branch on job type.
  • Existing rows: any PM already sitting in ServiceCompleted moves queue the moment this ships — it leaves every operator's tab and appears in the planner's. Nothing is rewritten in the database, so this is reversible by reverting the code.
  • Videos: technician chapter 2 (the submitted-status slide) and reporter chapter 4 need re-shooting; the reporter script line "PM jobs also appear here" comes out.

Not in scope unless you say so

  • A manager or QA counter-signature on the PM sheet after the planner accepts.
  • Auto-accepting a PM with no NG items — tempting, but it would put a signature on a sheet nobody read.
  • Letting the planner accept CM/BD "on behalf of" a reporter who is on another shift.
