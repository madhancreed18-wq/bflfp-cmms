Plan against actual, task by task

The other half of the S-curve. The curve says the project is ahead; this says which tasks are, and which are not.

1 · Why this and not just the S-curve

The S-curve gave one number for the whole project: +53 hours ahead. It is true, and it hides two things a supervisor needs before Monday:

  • Which tasks slipped. A project can be ahead overall while the one task everything else waits on is a week late.
  • Whether the finish date still holds. Hours earned say nothing about dates; only the tasks at the end of the chain do.

Two bars per row answer both. The upper bar is the baseline — what was agreed on day one, which never moves. The lower is what actually happened.

5 · What it costs to build

Three things, and two of them the app already records:

  • date_start, date_end — the baseline, set once when the project is approved and then locked. A baseline that gets quietly edited is not a baseline, so changing it is a deliberate act that says who moved it and why.
  • Actual start is already recorded: it is started_at, stamped when the technician presses Start. Actual finish is done_at. Neither needs a new field or a new habit.
  • waits_for — the one genuinely new field: which task this one cannot start before. One dropdown per task, filled in once when the project is written.

So the actual bar draws itself. The only things anybody types are the baseline and the order of the work, once each.

And waits_for is not optional detail — it is the whole forecast. Without it, a task that has not started keeps its original dates no matter how late the task before it ran, every un-started row reads "on time", and the chart cheerfully reports a handover date that cannot happen. With it, the 5 days lost on the foundations arrive at the handover row where somebody can still do something about them.

One decision. When a task finishes late, does the baseline for everything after it move with it? Two honest answers:
  • No — the baseline is frozen. Every later task keeps its original dates and the slip shows up as a growing red tail. Brutal, and it is what a review meeting needs.
  • Yes — re-plan on demand. A "re-baseline" button shifts the remaining tasks and records that it happened. Kinder, but a project that is re-baselined every fortnight always looks on time.
My recommendation: frozen by default, with re-baseline as a deliberate button that stamps who pressed it — so the history of the slip survives.
Both charts, one page. This and the S-curve are the same data seen twice: the curve for the trend, the timeline for the detail. They belong on the same project screen, curve on top, timeline under it.
